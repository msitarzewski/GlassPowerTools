# Part 1 — D27: every saved connection has a host record

## The surface, enumerated rather than assumed

Every construction of a saved record in the three capabilities, found by searching for the
constructor rather than for the word "create":

| Site | What it is | D27 target? |
|---|---|---|
| `ServerFormViews.swift:362` → `saveStandalone` | Add Server, and the Tailscale device import that feeds it | **Yes** |
| `SettingsManager.swift:1038` | `ssh_config` import, one per `Host` | **Yes** |
| `ServerFormViews.swift:388` | `configuration(id:address:name:)`, a pure function taking an id | No — creates nothing |
| `TerminalTailscaleView.swift:266` | Tailscale **Quick Connect** → `.quickConnect(config,…)` | No — transient, never saved |

| `DesktopServiceDraft.swift:210` | the desktop's shell draft | No — already has a link |
| `Debug/DesktopSpatialPreview.swift:34` | a preview | No |

**So D27 has exactly two live targets**, which is what was reported before the survey and is now
established rather than believed. The database has no link-less path at all.

## The one new finding: `.rdp` import is not connected to anything

`RDPFileImporter` (`Sources/GlassDesktop/RDPFileImporter.swift`, 212 lines) constructs a
`DesktopConnection` at `:99` — and **has zero references in the entire repository.** Not in
`Sources`, not in `App`, not in `Tests`, not in `UITests`. It was moved in Stage 4 W1 and never
wired, and the Stage 4 plan's open decision 2 — *"keep as a shell import command? Recommend yes"* —
was never answered.

That is **the eighth occurrence** of the defect class recorded since Stage 2: the machinery exists,
documented, and nothing joins it. It is also untested, because nothing calls it.

**Decision needed from the user, and it is small:** wire it as a shell import command, or delete it.
It is not a D27 target while it is dead, but it becomes a third one the moment it is connected — so
it is cheaper to settle now than to discover later.

## What "raise the host record behind the scenes" has to decide

Four questions the mechanism cannot avoid. Recommendations given; none is expensive.

**1. Attach to an existing host, or always make a new one?**
Recommend **attach when the address matches**, normalised, else create. Importing an `ssh_config`
that contains a machine already in the library should add a Terminal service to *that* machine, not
stand a second barn next to it. The shell already has `canonicalID(for:)` and
`consolidateRecords(of:)` for the merge case; what it lacks is an address lookup, which is a small
addition over `records`.

**2. What is the host called?**
The `ssh_config` alias, or the Add Server form's Name — the same string the user typed. The service
keeps its own display name from the capability's `serviceDisplayName(hostName:)`, as every other
service does.

**3. What happens when the host write succeeds and the server write fails, or the reverse?**
The order is already settled everywhere else and must not be reinvented: the capability commits its
record first, then the shell records the link (`GlassShellModel.swift:756-760`), so a service never
exists half-made. Under D27 the host has to exist *before* the configuration can be written to its
link, so the order becomes host → link → configuration, with the host and link rolled back if the
configuration fails. `GlassServiceDraft.rollback(endpointID:)` already exists for exactly this and
is what the shell's own setup flow uses.

**4. What does the import do when one of twelve hosts fails?**
Unchanged from today: `importSSHConfig` already collects a per-`Host` warning and continues
(`SettingsManager.swift:1051-1054`). A host that cannot be created becomes one more warning, and the
other eleven still land.

## Mechanism

A closure on `GlassTerminalRuntime`, set by the composition root, mirroring
`GlassDesktopRuntime.hostAccess` (`GlassDesktopCapability.swift:45`) so the capability never holds
the shell model (project rule 6). Shell side is already public: `addHost(displayName:address:…)`
and `addService(kind:displayName:endpointID:)`.

The closure's signature deals in plain values, not `ServerConfiguration`, because that type is
internal to the terminal: `(name: String, address: String) async throws -> EndpointID`. The caller
then builds its record with that id — which is the whole point, since `EndpointID.rawValue` already
*is* the record's id in all three capabilities.

**When the closure is nil** — a unit test, a preview — creation behaves as it does today. That keeps
the 30-odd existing terminal tests meaningful instead of forcing a shell into every one of them.

## Test surface

`saveStandalone` and `importSSHConfig` are exercised from `Tests/GlassTerminalTests/glas_shTests.swift`
only; the UI tests drive Add Server through the interface (`add-server-username` and friends in
`UITests/GlassShellLibraryUITests.swift:149` and `UITests/GlassTerminalUITests.swift:206`).

With the closure nil by default, the unit tests are unaffected. The **UI** tests run against the
real app and will start creating host records — which is correct, and is also what the tests should
now assert: after importing, the machine is *in the library*. That assertion is the proof D27 works,
and no unit test replaces it.

# Part 2 — D28: the usage index

## It already exists, twice, and must not be written a third time

| Site | What it does |
|---|---|
| `SettingsManager.swift:581` | `servers.contains { $0.sshKeyID == entry.key.id }` — "is this key still referenced?" |
| `SettingsManager.swift:847` | `.filter { $0.sshKeyID == keyID }.map(\.id)` — the servers using a key, during deletion |

**Extract these into one named type and route both through it.** Writing a third would be occurrence
nine of the same defect class, in the same session that recorded the eighth.

Proposed shape, derived and cheap:

```
GlassCredentialUsage
  .services(usingKey:)   -> [(host: HostProfile, service: HostServiceLink)]
  .count(usingKey:)      -> (readable: Int, unreadable: Int)
```

The second half of that tuple is not decoration; see the undecodable rule below.

## What is *not* a violation of "never stored", and must not be deleted by someone enforcing it

`SSHKeyDeletionJournal.referencedServerIDs` (`SettingsManager.swift:846-851`, capped by
`maximumReferencedServers`) durably records which servers referenced a key **at the moment a
deletion began**. That is not a usage table — it is a crash-recovery record of an in-flight
operation, and it is what lets an interrupted key deletion be reconciled at startup
(`reconcileSSHKeyDeletionJournalAtStartup`). D28 forbids a *standing* index of who uses what. It
does not forbid a journal of what an operation was part-way through doing. Stated here because the
two look alike and one of them is load-bearing.

## A stage 1 landmine found while surveying this

`SettingsManager.swift:574` reads **`UserDefaultsKeys.servers` straight out of defaults**, bypassing
`ServerManager` entirely, to verify key references during deletion recovery:

```swift
guard let data = sshKeyDefaults.data(forKey: UserDefaultsKeys.servers) else { … }
```

D26 stage 1 deletes that key. This read must move to the store, and it is exactly the "second index
over the same data" hazard the stage 1 plan warned about — found by grepping for the *key*, not for
`ServerManager`.

## Detach has a silent re-attach waiting for it

`TerminalServiceDraft.normalizeSelectedSSHKey` (`ServerFormViews.swift:412-418`), called from the
form's `onChange` at `:493-500`, does:

```swift
if let selected = sshKeyID, availableIDs.contains(selected) { return }
sshKeyID = settingsManager.sshKeys.first?.id
```

So a service whose `authMethod` is still `.sshKey` but whose `sshKeyID` is nil **silently acquires
the first key in the library** the next time its form is opened. Detaching from the key manager and
leaving `authMethod` alone would therefore un-detach itself, quietly, later, and point the service at
a key the user never chose.

**So detach is not `sshKeyID = nil`.** It must leave the service in a state the normaliser respects:
either the replacement the user picks in the confirmation, or an explicit *needs setup* that the
normaliser does not overwrite. This is the single most important line in this plan, and it is the
same shape as the publish/redact–apply/re-attach pair in stage 3: a half-implemented change that
passes every test and undoes itself in use.

## The two consequences that belong in the confirmation

1. **A service left with no credential cannot sign in.** The sentence already exists for the
   no-configuration case — *"… has no saved terminal configuration. Edit the service to set it up,
   or remove it."* (`GlassTerminalCapability.swift:227`) — and the no-credential case needs its own,
   in the same voice.
2. **Detaching a Secure Enclave key changes where the service exists.** Binding is derived from the
   credential (D26 stage 3), so detaching stops a terminal being device-bound and it **starts
   appearing on other devices**; attaching one makes it vanish from them. Said at the point of
   choice, not discovered on another device.

## The undecodable rule, designed in rather than retrofitted

A configuration this build cannot decode is skipped, not fatal (`GlassServiceStore.swift:44-47`).
So a key could read *used by 0* while a service written by a newer build still references it — and
then be deleted. "Used by" therefore reports **"2 services, plus 1 this build can't read"**. A zero
only ever proves where you looked (project rule 24). A key genuinely used by nothing says so
plainly: that is the state after the juliet deletion in the user's scenario, and the signal that
it is safe to delete.

## Scope, measured

`sshKeyID` appears in six files, **all the terminal's**. Passwords are keyed per service
(`KeychainManager.serverPasswordAccount(for:)`), RDP and database credentials are one per service,
and the database holds no key at all — it borrows the host's forward (D7). So the panel is a **key**
manager with a usage list plus flat 1:1 inventory rows, not a general auth registry.

# Order

1. **D27 mechanism** — the runtime closure, both call sites, host↔link↔configuration ordering and
   rollback. Independent of D28.
2. **D26 stage 1 remainder** — catalog-backed store, `UserDefaultsKeys.servers` deleted, including
   the `SettingsManager.swift:574` landmine above.
3. **`GlassCredentialUsage`** — extract the two existing lookups, add the unreadable count.
4. **Detach semantics** — the normaliser fix first, because without it detach undoes itself.
5. **The key manager panel** (D26 stage 4) then reads all of the above rather than excavating it.

# Execution log — D27

## Built 2026-09-15 — both paths adopt a host

`GlassShellModel.adoptService(kind:hostName:address:serviceName:)` finds or creates the host for an
address and links a service to it, returning the endpoint id the capability saves under.
`discardAdoption(_:)` undoes it when the capability then fails to write its own record — the same
orphan D25 exists to prevent, arriving from the other direction.

**Reuse is by address, case- and diacritic-insensitively**, so importing an `ssh_config` that names
a machine already in the library adds a service to that machine rather than standing a second record
beside it. The existing record keeps its own display name; an import does not rename a machine the
user already named.

The capability side is two closures on `ServerManager` — `adoptHost` and `discardAdoption` — set by
the composition root, because a capability must not hold the shell model (rule 6). `ServerManager`
rather than the runtime because both call sites already hold a `ServerManager` and neither holds the
runtime. **When they are nil, creation behaves exactly as before**: a fresh `UUID()` and no host
record, which keeps the existing terminal tests meaningful instead of forcing a shell into each one.

Call sites: `TerminalServiceDraft.saveStandalone` (an edit keeps the id it has; only a new server is
adopted) and `SettingsManager.importSSHConfig` (one adoption per `Host`, and a failure is still one
warning rather than a failed import).

## The test that passed with the logic defeated

`aSecondServiceAtTheSameAddressJoinsTheMachineAlreadyThere` originally asserted
`model.catalogHosts.count == 1` — and passed with address reuse disabled. **`GlassShellHostGrouping`
already merges records that share an address into one library row**, so a duplicated *record* is
invisible in the grouped view. The assertion moved to `model.records`, and only then did defeating
the reuse make it fail.

That is the rule earning its keep twice in one session: a test written against the wrong projection
looks exactly like a passing test.
