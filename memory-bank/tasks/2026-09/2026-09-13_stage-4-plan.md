# Stage 4 and 4.5 — the remote desktop capability, planned from a measured survey of glassDT

Owner: coordinating agent. Written 2026-09-13. **Status: PLAN, awaiting approval.**

**Shape, set by the user:** Stage 4 moves what glassDT already does, feature for feature, and
changes nothing. Stage 4.5 then adds the missing and planned features — the same way Stage 3 shipped
the Database capability and Stage 3.5 followed with continuity.

**Supersedes the module table and sizing of** [the 2026-09-10 draft](2026-09-10_stage-4-desktop.md),
which was written before glassDT was measured, before `GlasSecretStore` was absorbed, and before
D23–D25. That note's *deletion list* and *validation ledger* remain correct and are carried forward.

## Task

- **Objective, Stage 4:** glassDT at parity — RDP **and VNC/Apple Screen Sharing** sessions, Metal
  presentation, input mapping, clipboard, audio, cursor decoding, display resize, `.rdp` file
  import, and the spatial canvas on visionOS — as a capability of this shell, with glassDT's
  three-process machinery deleted and its settings folded into the one settings surface.
- **Objective, Stage 4.5:** the eight named gaps below, headed by the one measurement nobody has
  taken — a signed-in Apple Screen Sharing session.
- **Authorization:** the user, 2026-09-13, noted that glassDT works and asked for a plan to
  migrate its functionality feature for feature, with a preference to focus on the desktop
  screen-sharing features. This note is the plan; **building starts on the user's word.**
- **Inputs, read-only:** `../glassDT`. It is obsolete and does not compile; it is a record to read.

## What the user asked for that the old plan did not cover

**Screen sharing is in scope now, not Stage 5.** The 2026-09-10 draft deferred VNC — the `.vnc`
service kind, the VNC credential record and VNC-over-SSH — to Stage 5. Its stated reason was that
the sibling apps could not decode a kind they did not know. **That reason is void:** the source apps
are obsolete and no longer read the catalog. The user's own framing is screen sharing, which is
VNC and Apple Screen Sharing specifically, so VNC moves in Stage 4 beside RDP.

`HostServiceKind` is `rdp, ssh, database` (`../GlassConnectionKit/.../HostProfile.swift:19`), and
**it does not need a fourth case.** glassDT models the RDP/VNC choice as a field on the connection,
so screen sharing arrives in Stage 4 with no catalog schema change at all — see *Two stages* below.
Promoting `.vnc` to a service kind stays available as a Stage 4.5 decision.

### The dependency risk that dominated Stage 3 does not exist here

Stage 3's top risk was a swift-crypto conflict, resolved only by actually resolving. The equivalent
check here is already answered:

| Package | RDPKit demands | This project already resolves (`Package.resolved`) |
|---|---|---|
| swift-nio | `exact: "2.102.0"` | **2.102.0** |
| swift-nio-ssl | `exact: "2.37.4"` | **2.37.4** |

VNCKit declares **no package** dependencies; the two transports depend only on RDPKit and VNCKit.
So **the engine move adds zero new external packages.** This is read off the manifests and the lock
file; it is still to be *proven by resolving* in W1, per the Stage 3 lesson.

**One thing that must travel with VNCKit or the move silently loses an encoding.** VNCKit's target
carries `linkerSettings: [.linkedLibrary("z")]` (`../glassDT/Packages/VNCKit/Package.swift:9`) — the
system zlib, which is what `ZlibInflater` and therefore the **Zlib and ZRLE** encodings depend on.
Folding the package into a root target drops the manifest that declares it, so the setting has to be
restated on `Sources/VNCKit`. It would not fail to compile; it would fail to link, or link against
nothing and lose the two best encodings. W1 must assert ZRLE decodes after the move, not just that
the target builds.

### RDPKit is a vendored third-party fork — it goes in `Packages/`, not `Sources/`

**This corrects an earlier draft of this note**, which placed RDPKit in `Sources/` by analogy with
the GlassDBKit move. The analogy fails on the fact that decides it:

> Upstream: `https://github.com/steelbrain/RDPKit`. Baseline `2032fdbc9a30…` (RDPKit 0.3.1).
> The upstream MIT license and Steelbrain copyright remain.
> — `../glassDT/Packages/RDPKit/GLASSDT-PATCHES.md:3-6`

RDPKit is **not our code**. The Stage 3 note's own stated reason for putting GlassDBKit in
`Sources/` was *"It is **our** code. `Packages/` holds the two vendored third-party forks; mixing
our engine in with them blurs that boundary."* RDPKit is a vendored third-party fork, so the same
sentence puts it in `Packages/RDPKit`, beside Citadel and swift-nio-ssh.

The split is therefore:

| Moves to | Why |
|---|---|
| `Packages/RDPKit` | vendored fork of steelbrain/RDPKit 0.3.1, MIT, Steelbrain copyright |
| `Sources/VNCKit` | **ours** — "written from RFC 6143 and the public RFB protocol registry; no third-party VNC source was copied or linked" (`../glassDT/THIRD-PARTY-NOTICES.md`) |
| `Sources/GlassRDPTransport`, `Sources/GlassVNCTransport` | ours — adapters authored for the app |

**The cost of keeping RDPKit a nested package: its two `exact:` pins stay.** They match what this
project resolves today (2.102.0 / 2.37.4), so nothing breaks now, but they freeze the whole graph's
NIO versions from the next bump onward. Relaxing them to ranges is a one-line local patch — and
`GLASSDT-PATCHES.md` is exactly the file that exists to record such a change. Recommend doing it in
W1 and recording it there, rather than accepting a frozen NIO.

### The local patches are security work and must not be lost in the move

`GLASSDT-PATCHES.md` records hardening applied on top of upstream. These are the reason "just take
upstream RDPKit" would be a downgrade:

- The TLS certificate is authorized **before** CredSSP or Client Info credentials are sent; hiding a
  warning never grants trust.
- TLS minimum and maximum are both 1.2. When an application requires NLA there is **no silent
  downgrade**.
- Cross-host redirection requires explicit opt-in; pins do not transfer endpoints.
- Incomplete auxiliary input/cursor/microphone dynamic channels are rejected with a CREATE failure by
  default; `allowsAuxiliaryInputChannels` exists only for upstream compatibility and glassDT leaves
  it **disabled**.
- No input, clipboard or display writes are scheduled on already-inactive channels.
- `RDSTLS.swift` is local work: GNOME Remote Desktop 50.2 returns `LB_PASSWORD_IS_PK_ENCRYPTED`
  after initial NLA, and the client negotiates RDSTLS **only** for that authenticated handoff,
  keeping the password blob opaque, validating the target certificate container, and requiring the
  presented certificate to match it exactly. The original password is never reused.

W6's security spot-check re-verifies each of these at its trust boundary rather than assuming a file
copy preserved them.

## VNC engine — what it actually speaks (survey, 2026-09-13)

`Packages/VNCKit/Sources/VNCKit`, 1,482 lines across 10 files. `VNCClient.swift` (363) is the front
door; `RFBEncodings.swift` (246) does the pixel work.

- **Protocol:** accepts `RFB 003.xxx` with minor ≥ 3, collapsing to 3.8 / 3.7 / 3.3
  (`RFBModels.swift:25-44`). **Apple's `RFB 003.889` is handled deliberately by that clamp**, with a
  comment saying so (`RFBModels.swift:23-24`) — the one line that makes Screen Sharing reachable.
  3.3 takes the server-selected-security path, 3.7/3.8 the client-chooses path
  (`VNCClient.swift:103-116`).
- **Encodings, all implemented** and advertised in preference order
  (`RFBModels.swift:75-76`, sent at `VNCClient.swift:194-199`): ZRLE (16), Hextile (5), Zlib (6),
  CopyRect (1), RRE (2), Raw (0), Cursor (-239), DesktopSize (-223), ExtendedDesktopSize (-308),
  LastRect (-224). ZRLE covers subencodings 0, 1, 2–16 palette, 128 RLE and 130–255 palette-RLE
  (`RFBEncodings.swift:126-205`); Hextile covers all five subencoding bits
  (`RFBEncodings.swift:74-120`); CopyRect is memmove-safe for overlap
  (`RFBFramebuffer.swift:71-87`); RRE bounds-checks subrects (`RFBEncodings.swift:49-70`).
  ExtendedDesktopSize handles the screen list and the resize-refusal status
  (`VNCClient.swift:276-304`).

Nothing here is stubbed. This is a complete small RFB client, and it is the reason screen sharing is
a reasonable Stage 4 ask rather than new work.

## RDP engine — the security surface, and its named limits

- **TLS is pinned to 1.2 at both ends, deliberately.** `ConnectionPreflight.swift:2827,2830`, with
  the reason in-code at `:2828-2829`: Windows RSA certificates lacking `digitalSignature` break
  BoringSSL's TLS 1.3 certificate path. This is a documented interoperability constraint, not an
  oversight — and it is the kind of thing a later "modernise the TLS floor" change would break.
- **Certificate trust is evaluated by the engine, not by NIOSSL** (`:2825`), which is what makes the
  explicit SHA-256 leaf pinning and the "authorize before credentials" ordering possible.
- **CredSSP/NLA implemented** (`CredSSP.swift`, 663 lines), **NTLMv2 only** (`NTLM.swift`, 733 lines;
  MD4 implemented in-tree at `:509` because CryptoKit does not provide it).
- **SPNEGO carries the NTLM mechanism only. There is no Kerberos** — zero matches across the engine.
- **Required-NLA cannot be silently downgraded**: `ConnectionPreflight.swift:1237-1239` throws
  `protocolViolation("server did not negotiate required Network Level Authentication")` when NLA was
  required and neither CredSSP nor RDSTLS was selected.

`ConnectionPreflight.swift` (7,025 lines) is **misnamed**: it is the whole session driver — connect,
negotiate, TLS, NLA, MCS, licensing, activation, finalization and the live receive loop — not a
preflight check. Worth renaming during the move, and worth knowing before anyone goes looking for
the connection code somewhere else.

## What "feature for feature" actually buys — the RDP capability is narrow

`Packages/RDPKit/CAPABILITY-LEDGER.md` is the honest ledger, and its own framing line is
*"This records the production facade's implemented surface, not a claim of complete RDP
implementation or Microsoft certification."* It and `GLASSDT-PATCHES.md` are the two most valuable
non-code artifacts in that repo and **both move with the engine.**

Quoted from the ledger — **not implemented or exposed:**

> RD Gateway, Kerberos, legacy Standard RDP Security/RC4, UDP multitransport, AVD/broker login,
> RemoteApp, drive/printer/smart-card/USB redirection, camera/microphone capture, multi-monitor UI.

Confirmed by grep over the engine, 2026-09-13: **zero matches** for `gateway`, `kerberos`,
`remoteapp`, `multitransport`, `rdpeudp`. `spnego` hits only `CredSSP.swift:301-315` and
`ConnectionPreflight.swift:3093`, and that wrapper carries **NTLM only**. `RDPNegotiation.swift:14`
defines `rdsAAD = 0x10` but never places it in the request set (`ConnectionPreflight.swift:1534-1536`)
— a dead constant, not a feature.

**Stated plainly, because a feature-for-feature migration inherits it: a user on a corporate network
cannot connect to**

1. **anything behind an RD Gateway** — which is how the large majority of enterprise RDP is
   published, on 443 rather than 3389 direct. No tunnel exists, so it cannot even be attempted;
2. **Azure Virtual Desktop, Windows 365, or any broker-fronted deployment** — no broker, no
   connection-broker redirection;
3. **any host whose domain requires Kerberos** — RestrictedAdmin, Remote Credential Guard, or a
   policy that disables NTLM. NTLMv2 is the only mechanism offered;
4. **RemoteApp** published-application sessions;
5. **smart-card / PIV logon** — the capability is parsed and discarded
   (`DeviceRedirection.swift:337-341`).

What *does* work: a directly reachable Windows host on 3389 with NTLM permitted. A real slice, and a
narrow one. **None of this is a defect to fix in Stage 4** — it is the shape of what is being moved,
and it should be decided knowingly rather than discovered after the move.

Other per-row limits from the ledger, carried so they are not re-lost:

- ~~Transport/security — *"No real Windows NLA host tested."*~~ **Closed 2026-09-14:** Windows 11
  Pro, NLA required, certificate pinned, 1280x800 frame in 0.84s. See
  [live hosts](2026-09-14_stage-4-live-hosts.md).
- Primary graphics — *"Immutable full-frame BGRA publication requires copies."* **Not zero-copy.**
- RDPGFX — *"AVC444 is RDP-specific reconstruction… No real Windows AVC444/performance claim."*
- BCGR drawing orders — *"All 32 orderSupport bytes are zero"*, and every cache capacity is zero.
- Clipboard — file clipboard APIs exist upstream but **are not exposed**.
- Audio — no physical audible-output test; microphone capture not exposed.
- Input — physical iPad and visionOS keyboard validation still outstanding.

### The certificate path is correct, and reads alarming out of context

`ConnectionPreflight.swift:2825` sets `certificateVerification = .none`. Verified directly rather
than taken on report: the next line says *"Trust is evaluated with Security.framework below before
sending application data"*; the real evaluation is `SecTrustEvaluateWithError` at `:6968`; and
`:2877` throws `"server certificate identity was not authorized"` **before** any credential is sent.
`CertificateTrust.swift:3` states the invariant: *"The certificate must be authorized before any
CredSSP or RDP credentials are sent."* NIOSSL verification is disabled because the engine must do
system trust evaluation **plus** SHA-256 leaf pinning itself, which NIOSSL cannot express.

**Record this here so no future reader "fixes" it.** A reviewer who greps for
`certificateVerification = .none` and stops there will file it as a vulnerability; it is the opposite.

## Screen sharing: the two findings that shape the wave

### 1. Apple offers two security types; we implement one

`RFBSecurityType` has four cases only — invalid(0), none(1), vncAuthentication(2),
appleRemoteDesktop(30) (`RFBModels.swift:47-51`). **VeNCrypt(19), TLS(18), Apple type 35, SASL and
UltraVNC MS-Logon have no case and no branch.**

This Mac's own Screen Sharing service **offered types 30 and 35**, and the client took 30
(`../glassDT/Documentation/Verification/VNC/README.md`). So type 30 is the path, and it is
implemented properly: DH over a hand-rolled `BigUInt`, prime bounds-checked 16…1024 bytes, AES-128
keyed on MD5 of the shared secret, credentials placed in a 128-byte random block, and **private key,
shared secret, AES key and credential block all zeroed in `defer`** (`RFBSecurity.swift:38-79`).

The open risk is that type 30 is the *older* exchange and 35 is what a current macOS may come to
prefer or require. **Stage 4.5 item 1 is what tells us**, and it is the same test that has never been run. If the server insists on 35, screen sharing against modern macOS is new
protocol work, not a move — and that is the one thing in this stage that could turn out much bigger
than it looks.

### 2. VNC is plaintext, so VNC-over-SSH should not wait for Stage 5

**There is no TLS anywhere in VNCKit** — the only `tls` token in the module is inside an `NWError`
description string (`RFBNetworkChannel.swift:102`). After the handshake, framebuffer contents and
every keystroke travel in the clear.

Both the mitigations a VNC client normally has are absent: VeNCrypt(19) and TLS(18) are not
implemented, and the ARD exchange protects *only the credentials*, not the session.

The 2026-09-10 draft deferred VNC-over-SSH to Stage 5. It is not a convenience — it is the **only**
confidentiality this capability can have, so it should not wait that long. **Stage 4.5, item 3**,
which is the first stage where new work belongs at all. It is small: `GlassSSHTransport.forward`
already exists, D7 already established a capability borrowing the host's own SSH forward (the
database capability does exactly this), and the byte-source seam is already there. The session UI
should show an encrypted/unencrypted indicator so the difference is visible rather than assumed.

### VNC-over-SSH: the seam already exists

Forwarding is **entirely absent** — no `tunnel`, `portForward`, `socks`, `proxy`, `jumphost` or
`bastion` anywhere in the app layer or either transport, and `GlassVNCSession` always opens a bare
`NWConnection` over `NWParameters.tcp` (`GlassVNCSession.swift:43, 94-96`;
`RFBNetworkChannel.swift:7-23`). The `ssh` tokens in the app layer are host-catalog *pairing*
labels that hand off to glas.sh over a `glassh://` URL — not a transport.

**But the insertion point is already there and already exercised.**
`VNCClient.init(configuration:callbacks:source:sink:open:close:)` (`VNCClient.swift:50-59`) accepts
any `RFBByteSource`/`RFBByteSink`; the tests drive it with `MemoryByteSource`/`MemoryByteSink`
(`ByteIO.swift:75-93`). Pointing that seam at `GlassSSHTransport.forward` is the whole job. This is
why Stage 4.5 can carry VNC-over-SSH without becoming a rewrite.

## Lifecycle and presentation — what moves, and the one gap that is new work

### Lifecycle is thorough, and worth preserving deliberately

Not a naive connect/disconnect. Each behaviour below is easy to lose in a move and must be
re-asserted, not assumed:

- **Attempt isolation** (`DesktopSessionModel.swift:213-232`): every attempt takes a new `attemptID`
  and a **new transport instance**, the old one disconnected on a detached task, and every callback
  re-checks `requireCurrent` (`:234-236`). This is what stops a slow previous attempt writing into a
  newer session.
- **Cancellation is synchronous** (`stopCurrent()` `:395-408`) so closing a window invalidates
  immediately; `close()` (`:415-428`) returns a *memoised* cleanup task, and `isolated deinit`
  (`:160-165`) cancels all four tasks.
- **Cleanup is complete**: tasks cancelled, audio stopped, frame/capabilities/clipboard/screens/
  cursor cleared, and the wallpaper store rotated with its files deleted.
- **Resize coalescing** at 250 ms for window-follow, 100 ms edge, 50 ms scale change, each geometry
  bumping `resizeRevision` and cancelling the pending task (`:450-513`).
- **Input backpressure**: a 512-event cap with consecutive moves coalesced; overflow halts the queue
  with "Remote input could not keep up" (`DesktopInput.swift:52-62`).
- **Trust re-check on approval** (`:353-381`): `approveCertificate` re-verifies the issued request,
  the attempt ID, host and port and the retained in-memory credential before reconnecting.
- **Held-key release** is properly wired — on scene phase leaving `.active`
  (`DesktopSessionView.swift:240`), and before any input UI is shown (`:322, 362, 372`).

### The gap: there is no sleep/wake handling at all

**Verified directly, 2026-09-13: zero occurrences of `willSleepNotification`, `didWakeNotification`
or an `NSWorkspace` notification observer anywhere in `Sources`, `App` or `Packages`.** A machine
that sleeps mid-session recovers only by whatever error the transport eventually surfaces.

This project's own testing table requires it — *"Lifecycle: reconnect, cancellation, focus changes,
held-key release, **sleep/wake** and bounded cleanup"* (`AGENTS.md`, Testing Requirements). So this
is **required new work in Stage 4, not a parity item**, and it is the one behaviour on the lifecycle
list that cannot be satisfied by moving code. It is **Stage 4.5, item 4**.

### Metal presentation: proven to render, never measured

- `command.present(drawable)` at `DesktopMetalRenderer.swift:123`, `commit()` at `:130`.
- A **3-slot ring with `DispatchSemaphore(value: 3)`**, waited at `:111` and signalled in
  `addCompletedHandler` (`:126-129`) — correct GPU resource lifetime, which the family testing table
  asks about explicitly.
- **`isPaused = true` + `enableSetNeedsDisplay = true`** (`DesktopMetalSurface.swift:84-101`):
  on-demand redraw, not a vsync loop. Good for energy, and a detail that a careless port would turn
  into a 60 Hz spin.
- Upload is a **per-frame CPU copy** into a `.bgra8Unorm`, `.shaderRead`, `.storageMode = .shared`
  texture, reallocated only on dimension change (`:139-152`). Consistent with the ledger's
  *"immutable full-frame BGRA publication requires copies"* — **not zero-copy**, and honest about it.
- Presentation modes live in inline MSL (`:240-267`): original, remove-black, remove-wallpaper,
  cursor pass-through and key-colour, with
  `alpha = smoothstep(threshold, threshold + feather, distance) * opacity`, premultiplied.
  `sourceOrigin`/`sourceExtent` (`:17-20`) crop one display out of a multi-display framebuffer.

**Proven:** real-device GPU readbacks asserting exact pixels and `status == .completed` —
`GPUPresentationTests` (5), `ColorKeyPresentationTests` (8), `SpatialTextureTests` (3).
**Not proven:** no latency, FPS, energy or memory figure exists anywhere. Per the family rule,
Stage 4 may claim the pixels and must not claim the performance.

## Two stages, as Stage 3 was done — the user's structure, 2026-09-13

The user proposed treating Stage 4 as Stage 3 was treated: a stage and a "plus" stage in
sequence, the second covering the missing and planned features.

**Stage 4 moves what exists. Stage 4.5 adds what does not.** The dividing line is a single testable
rule:

> **If Stage 4 changes a behaviour, that is a bug.**

That is worth more than it sounds. This is a **41,500-line move**; mixing new protocol work into it
destroys the only cheap way to diagnose a failure, which is "it worked in glassDT". Everything new —
however small and however desirable — waits for 4.5, where it can be judged on its own.

### The split is cheaper than expected, because VNC needs no schema change

An earlier draft of this note put `.vnc` in `HostServiceKind` and called it Stage 4's one
irreversible step. **That is not required.** `DesktopProtocol` is a *field on the connection*, not a
service kind (`../glassDT/Sources/GlassDesktopCore/DesktopConnection.swift:11-19`):

```swift
/// Wire protocol of a saved desktop. Documents written before this field existed decode as RDP.
public enum DesktopProtocol: String, Codable, CaseIterable, Sendable {
    case rdp
    /// VNC/RFB, including Apple Screen Sharing on macOS hosts.
    case vnc
    public var defaultPort: UInt16 { self == .rdp ? 3389 : 5900 }
    public var displayName: String { self == .rdp ? "Remote Desktop (RDP)" : "Screen Sharing (VNC)" }
}
```

It already carries its own tolerant-decode rule. So the capability registers for `.rdp` and the
protocol field distinguishes, exactly as glassDT does — **no new enum case, no CloudKit schema
change, nothing irreversible in Stage 4.** Whether `.vnc` deserves to be a first-class service kind
becomes a 4.5 question, decided with the thing working in front of us.

## W2 findings from the running app

**A window sizes itself to whatever it is showing when it is created.** `DesktopSessionHost` shows a
`ProgressView` while the saved desktops load, so the window was created around a spinner and kept
that size — about 640 points — for the rest of its life. `DesktopSessionView` already carries
`maxWidth: .infinity` (`DesktopSessionView.swift:169`), which lets it *fill* a window but never
*grow* one, so the session then rendered inside a window far smaller than its `.defaultSize`, the
toolbar collapsed into an overflow chevron and every label truncated.

The fix is one line, and it is glassDT's: the scene wrapper ends with
`content.frame(maxWidth: .infinity, maxHeight: .infinity)` (`../glassDT/App/glassDTApp.swift:79`).
Reported by the user against 0.4.91 with a screenshot.

**The same shape exists elsewhere and is deliberately not being changed in Stage 4.**
`GlassDatabaseScenes`' workspace window has an `else` branch showing a `ContentUnavailableView`
(`GlassDatabaseScenes.swift:33-39`) with no greedy frame on the wrapper, so a workspace opened
without a resolvable id would shrink the same way. It is rare, it predates this stage, and Stage 4's
rule is that it changes nothing outside the move — so it is recorded here as a **Stage 4.5**
candidate rather than fixed in passing.

## Validation — what glassDT proved, and what this stage must re-prove

glassDT's ledger (`../glassDT/VALIDATION.md`, `Documentation/Verification/`) is unusually strong and
is the parity bar:

| Proven there | Must be re-proven here |
|---|---|
| RDPKit 1013 tests; full synthetic NLA → RDSTLS → desktop | the suite, after the move |
| A real user host: initial NLA, encrypted RDSTLS handoff, decoded frames, source resize, clean disconnect | the same host, after the move |
| TigerVNC 1.13.1 in a container: RFB 3.8, auth, first frame 73 ms, input echoed, `SetDesktopSize` accepted | `Tests/IntegrationVNC/run.sh` moves and runs |
| Apple Screen Sharing: `RFB 003.889` negotiated, ARD Diffie-Hellman exchange accepted as well formed | unchanged — and see below |

**Never proven, and this stage does not get to claim it:**

- **A signed-in Apple Screen Sharing session.** glassDT reached the auth exchange with a deliberately
  invalid account and got "authentication or authorization failure". Frames, input and resize against
  a real signed-in Mac are **unverified**. Given the user asked for screen sharing by name, this is
  the headline gap and should be the first live test of W3 — it needs the user's own Mac account, so
  it is theirs to run, and no credential is recorded anywhere.
- Apple's High Performance mode, HDR, audio or virtual displays — **none of it is implemented.**
- Physical-device VNC performance, latency or energy on any device.
- Non-Apple VNC servers other than the TigerVNC fixture.
- Two glassDT open items re-inherited: GNOME sign-out window behaviour, and whether the RDP Detail
  scale setting sharpens text on the Ubuntu host.

## Open decisions for the user

1. **Run Stage 4.5 item 1 before Stage 4 starts.** The signed-in Apple Screen Sharing test is the
   one measurement that could change the size of everything else, it costs an afternoon, and it
   needs no code. Recommend doing it now, out of order, and letting the result set 4.5's shape.
2. **`.rdp` file import** (`RDPFileImporter.swift`, 212 lines) — keep as a shell import command?
   Recommend yes; it is 212 lines and already parses off-main.
3. **Credential mobility default.** `DesktopConnection.init` sets `mobility = .deviceOnly`
   (`DesktopConnection.swift:56`), but D18/D23 made this project's credentials synchronize by
   default. Stage 4 must pick one deliberately rather than inherit glassDT's silently. Recommend
   following D18 — the whole point of Stage 3.5 was that the third credential kind arrives with its
   mobility already decided.
4. **How far Stage 4.5 goes.** Items 1–4 are, on the evidence, the ones worth doing. 5 (RD Gateway)
   is the largest single piece of value and the largest single piece of work; it is reasonable to
   stop before it, and reasonable to make it a Stage 4.6.
