# Stage 3.5 — continuity: one library and one set of credentials, on every device

**Date** 2026-09-13 · **Owner** coordinating agent · **Status: planned, approved by the user**
**Authorization:** *"We can't truly sync database sessions if the database passwords stay
app-private. That must change."*

## The requirement, in the user's words

> A user should define everything on Mac, then pick up Vision Pro and get to work without having to
> mess with settings and passwords. If they add a DB or Desktop on Vision Pro, when they get back to
> Mac it should just work.

Termius and SQLPro Studio do this. It is not novel; it is table stakes for a product whose whole
premise is *one library of hosts*, and the merged app is the first version of this family that could
honestly deliver it.

## Why this is a stage and not a task, and why it goes before Stage 4

1. **Stage 4 adds a third credential kind.** RDP credentials arrive with the desktop capability
   (`RDPCredentialStore` is already in `GlasSecretStore`). Deciding mobility *after* a third
   capability starts writing secrets means migrating three kinds instead of two.
2. **The record store changes shape.** The catalog's source of truth moves off the App Group. Doing
   that while Stage 4 is rewiring `DesktopAppModel`'s catalog would collide badly.
3. **It is the differentiator.** A spatial workspace where a host's terminal, database and desktop
   coexist is worth little if the Vision Pro cannot reach the hosts the Mac already knows.

## The distinction that has to be kept straight

These are **orthogonal** and were conflated in the security review's F3 and in the first reading of
it:

| Mechanism | Controls | Attribute |
|---|---|---|
| **Access group** | which *apps on this device* can read an item | `kSecAttrAccessGroup` |
| **Mobility** | whether an item reaches the user's *other devices* | `kSecAttrSynchronizable` |

The goal needs the second. It does **not** need the first — and with three apps merging into one,
cross-app sharing is losing its reason to exist. So F3 (database passwords written into the shared
Glass-family group, unreachable and never cleaned up) remains a bug to fix, **and** continuity is
achievable without it. Fixing F3 does not work against this stage.

## What already exists — the honest inventory

`GlasSecretStore` was built for this and then defaulted off:

- `SecretMobilityPolicy` with `.deviceOnly` and `.iCloudKeychain`
  (`Configuration/SecretStoreConfiguration.swift:42`).
- `validateMobility` (`Keychain/KeychainOperations.swift:226-240`) already enforces Apple's real
  constraints: Secure Enclave protection is refused (`deviceBoundProtection`), `*ThisDeviceOnly`
  accessibility is refused (`incompatibleAccessibility`), and the service must be in an
  **eligible list that already includes** `passwordsService`, `sshPasswordsService`,
  `rdpCredentialsService`, `sshKeysPrivateService`, `sshKeysPassphraseService`.
- `kSecAttrSynchronizable` is wired into every write (`:251`, `:285`, `:313`).
- The accessibility default already flips correctly: `.iCloudKeychain` selects
  `kSecAttrAccessibleWhenUnlocked` rather than `…ThisDeviceOnly` (`SecretStoreConfiguration.swift:83`).

**`iCloudKeychain` appears zero times in `Sources/` or `App/`.** The mechanism is complete and
unused — the same pattern as `DatabaseCommands` and `DatabaseSession.openForward`: every part
present, nothing joined.

The shell also has a generic iCloud key-value sync service already
(`GlassShell/GlassShellSettingsSync.swift`: writer identity, Lamport-revision envelope, deterministic
merge, quota/account status), and the entitlement `com.apple.developer.ubiquity-kvstore-identifier`
is declared on both macOS and the app target. **Only terminal themes and preferences use it**
(`GlassTerminal/ICloudSettingsSyncService.swift:172`).

## Apple's constraints, researched 2026-09-13

- **Only password-class items synchronize.** Certificates and cryptographic keys do not.
  *This does not block SSH keys here*, because `GlasSecretStore` writes everything as
  `kSecClassGenericPassword` (`KeychainOperations.swift:250,284,312,343,371`) — the key bytes travel
  inside a password item. That is why `sshKeysPrivateService` is already on the eligible list.
- **Secure Enclave keys can never sync.** They are hardware-bound. `validateMobility` already
  refuses them, which is correct and must stay.
- **`kSecAttrSynchronizable` and `*ThisDeviceOnly` are mutually exclusive.** Already handled.
- **Synced items are end-to-end encrypted** to the user's circle of trust; Apple cannot read them.
- **Do not use persistent references for synchronizable items** — they do not move between devices.
  Audit for these before enabling.
- **`NSUbiquitousKeyValueStore` is the wrong tool for the catalog:** 1 MB total, 1024 keys, and every
  write replaces the whole value with no partial update. Apple's guidance is the deciding line —
  *if you would call it "a value", use KVS; if you would call it "records" or "a list", use CloudKit.*
  A host library is records.

## Work breakdown

**1. Secrets (small, existing machinery).**
Select `.iCloudKeychain` for the eligible services. Fix F3 first so database passwords stop being
written into the shared app group. Audit for persistent references. Decide D21/D22.

**2. The catalog (the real work).**
Move the source of truth for hosts and services off the App Group onto CloudKit's private database
with `CKSyncEngine`. Conflict resolution matters: two devices editing the same host must converge,
and the existing Lamport-revision approach in `GlassShellSettingsSync` is prior art worth reading
even though the medium differs.

**3. Honesty in the UI.**
A clear account of what travels and what does not — passwords and SSH keys yes, Secure Enclave keys
no — plus sync status, because a silent failure here looks identical to a device that simply has not
synced yet.

## Validation — and this is the point of the stage

Everything here is **cross-device by definition**; a single-machine test proves nothing.

- Define a host with a database on the Mac; open the Vision Pro; connect without typing anything.
- Add a service on the Vision Pro; return to the Mac; find it there.
- The same for the iPhone.
- Edit the same host on two devices while one is offline; confirm convergence, not loss.
- Confirm a Secure Enclave key does **not** travel, and that the UI said so beforehand.
- Sign out of iCloud / disable Keychain sync and confirm the app degrades honestly rather than
  appearing empty.

Note the standing limitation this stage finally attacks: **every live database connection this
project has made was made from the Mac.** Stage 3's own R9 list still carries "iOS and visionOS are
compile-verified only" for real-server work.

## Risks

- **A synced secret is a bigger blast radius.** End-to-end encrypted to the user's circle, but a
  compromised device in that circle now reaches every credential. Worth stating in the UI.
- **CloudKit is a schema commitment.** Record types are hard to change once real data exists.
- **Two sync systems coexisting** (KVS for preferences, CloudKit for records) is a maintenance cost;
  D19 should say explicitly which belongs where so the boundary does not drift.


## Implemented 2026-09-13

**Secrets.** `.iCloudKeychain` selected for the database's app-private passwords, the shared
`sh.glas` credentials and the shell's. `authenticatedConfig` stays `.deviceOnly` and cannot be
otherwise: it is the `.requireAuthentication` policy, stored with `.userPresence` protection, which
`validateMobility` refuses for a synchronizable item — setting it there would not sync the secret, it
would make every write throw. Five tests guard the settings, including the two that fail silently
when wrong (accessibility must not be `ThisDeviceOnly`; the service must be on the eligible list).

**Records.** `GlassCatalogSync` (the rules) and `GlassCloudKitCatalogBackend` (the transport), with
CloudKit behind a protocol so the merge is testable without a network. Wired into `load()` and
attached in the app for real runs only — a UI test against an isolated directory has no business
talking to the user's iCloud account. Nine merge tests.

**Container.** `iCloud.com.glasspowertools` provisioned automatically under the existing automatic
signing; no developer-portal action was needed after all. Signed entitlements verified on macOS, iOS
and visionOS.

**Honesty.** Settings ▸ Privacy gained "On your other devices" (D20).

### The device checklist — everything this stage cannot prove on one machine

Not a formality: **no test here proves CloudKit delivers anything.** The merge is proven; the
transport is not.

1. Define a host with a database on the Mac; open the Vision Pro; connect **without typing a
   password**. This is the requirement in one action.
2. Add a service on the Vision Pro; return to the Mac; find it there.
3. The same for the iPhone.
4. Edit **different** hosts on two devices, one offline; confirm both survive — the case KVS could
   not have handled and the reason D19 chose CloudKit.
5. Delete a host on one device and confirm it does not come back from the other (the tombstone rule).
6. Confirm a `.requireAuthentication` service asks for its password again on the second device, and
   that Settings said so beforehand.
7. Sign out of iCloud and confirm the app degrades honestly rather than appearing empty.

**Still true and unchanged by this stage:** every live database connection this project has made was
made from the Mac.


## Observed on hardware, 2026-09-13 — CloudKit is delivering

**Checklist item 2 is met.** A host defined on the Vision Pro (`charlie`) appeared in the Mac's library
without any action on the Mac: the library went from three hosts at build 0.3.81 to five at 0.3.82,
and the additions match what the headset was showing. The user confirmed it.

This is the first evidence that **D19's transport works**, not just its merge rules. Every test in
`GlassCatalogMergeTests` proves what happens to two records once both are in hand; none of them
could prove a record crosses. Two devices and an iCloud account did in a way no unit test can.

**Still not demonstrated:** the tombstone rule across devices (item 5), convergence after an offline
edit (item 4), and iPhone (item 3).

## Found by using it, 2026-09-13 — SSH keys do not travel

The user: *"Not seeing the SSH keys shared though."*

**The secret travels and the record does not.** D18 put SSH private keys on the synchronizing
configuration and `sshKeysPrivateService` is on `validateMobility`'s eligible list, so the key
*material* reaches the other device. But the key **records** — id, name, algorithm, public key —
are persisted to `UserDefaults` under `UserDefaultsKeys.sshKeys`
(`GlassTerminal/SettingsManager.swift:230`), and App Group defaults are device-local. The second
device holds the secret and has no record that the key exists, so it lists none.

Exactly the shape D19 fixed for hosts: the secrets were never the problem, the catalog was.

**The Keychain cannot supply the missing half on its own.** `SSHKeyKeychainStore` keys its item by
`keyID.uuidString` and stores a bundle of private key plus passphrase — no name, no algorithm. So
enumerating `sshKeysPrivateService` on the second device yields ids and nothing to show for them.

**Bundling the metadata into that item would fix it and is the wrong fix**: this project's own
security rule is *"Keep metadata separate from secrets."* The records belong where the host catalog
already goes.
