# App icon — Icon Composer document with per-appearance artwork

2026-09-11. Coordinator, with W10 for the SVG attempt. **Shipped in 0.2.60**; committed
`226f98b → 8a4c8b5`.

## What ships

`App/GlassPowerTools.icon` — an Icon Composer document, three layers over a system-drawn
container. `ASSETCATALOG_COMPILER_APPICON_NAME = GlassPowerTools` in every configuration; the empty
`AppIcon.appiconset` and the separate `[sdk=macosx*]` icon-name override are gone.

| Layer | Dark / default | Light |
|---|---|---|
| Prompt (`>_`) | `prompt.png` | same file — the glyph sits on the red screen, so it is white in every appearance |
| Screen | `screen.png` | `screen-light.png` |
| Database | `database.png` | `database-light.png` |

Background `fill-specializations`: near-white gradient (0.985 → 0.945) for light, near-black
(0.11,0.115,0.125 → 0.035,0.038,0.045) for dark. Each group carries `specular: true`, a neutral
shadow and `translucency`. **Clear and tinted are derived by the system**, never authored — the
user's own contact sheet notes that live OS glass is backdrop-dependent.

## How the light variants are made

Not a redraw and not a flat grey. A gamma curve (γ 1.75, ceiling 0.98) is applied to the
**neutral** pixels only (saturation < 0.25) of the delivered renders, so highlights stay white while
midtones and shadows deepen enough to read on a near-white ground. The red screen is untouched.
Regenerating them is a short PIL script; the source of truth is the three delivered renders.

## Three things learned the hard way

1. **`image-name-specializations` exists.** A layer can carry different *artwork* per appearance,
   not only a different fill. That removed the apparent choice between the user's 3D renders and
   having light/dark/clear at all. Other `*-specializations` keys in `IconComposerFoundation`:
   `fill`, `glass`, `hidden`, `blend-mode`, `blur-material`, `lighting`, `asset-mirroring`.
2. **Flat SVG cannot stand in for a 3D render.** W10's four hand-authored SVG layers were correct
   and compiled clean, but per-surface bevels, occlusion and the glow under the database are not
   expressible as flat fills the system shades uniformly. Kept in history at `6a13027`/`863232c`
   if a flat family variant is ever wanted.
3. **An SVG viewBox maps to the icon grid, not the full canvas.** Geometry measured from a
   full-frame composite renders at ~82% and sits low; the SVG version needed a 1.22 scale about
   the centre to match. Raster layers do not have this problem.

## Verification

`xcrun actool App/GlassPowerTools.icon --compile <out> --platform macosx
--minimum-deployment-target 26.0 --app-icon GlassPowerTools --output-partial-info-plist <plist>`
compiles with zero errors; `xcrun assetutil --info <out>/Assets.car` shows
`NSAppearanceNameAqua`, `NSAppearanceNameDarkAqua` and `ISAppearanceTintable` for all three layers.
Renders were checked by extracting the compiled `.icns` with
`iconutil -c iconset` and comparing bounding boxes against the previous build: the red screen is
111×65 centred at (127,102) at 256pt, identical to the raster build that matched the composite.

**Limitation, unchanged:** the CLI renders only the default appearance. `iconutil` extracts one
rendition and `assetutil` reports structure without rendering, so **dark and clear are verified as
present, not as composited**. Seeing them means the installed app in Dark Mode, or Icon Composer's
live preview.


## visionOS had no icon at all — 2026-09-13

**Icon Composer does not support visionOS.** `App/GlassPowerTools.icon` produces a 2.4 MB
`Assets.car` plus an `.icns` for `--platform macosx` and **nothing whatsoever** for `--platform xros`
— an empty `<dict/>` partial plist and no catalog. The shipped visionOS bundle had **no icon keys in
`Info.plist` and no `Assets.car`**, so the app has been showing a default icon on the device since it
was first installed.

**Why this note did not catch it:** the Verification section above tested `--platform macosx` only.
The verification was real; it simply never covered the platform that needed it most. *A platform not
named in a verification is a platform not verified.*

Ruled out before concluding: adding `visionOS` — and then `xrOS` — to `supported-platforms.circles`
in `icon.json` changes nothing, and `--platform visionos` is not a valid actool platform at all.
Both edits were reverted. The limitation is Apple's, confirmed in their documentation and forums.

### What replaces it

`App/Assets.xcassets/GlassPowerTools.solidimagestack`, a layered visionOS icon built from the same
artwork, so the two icons cannot drift in content:

| Layer | Content | Source |
|---|---|---|
| Front | prompt glyph + database disc | `prompt-light.png` + `database-light.png` |
| Middle | the monitor | `screen-light.png` |
| Back | the document's own gradient, **opaque** | `fill-specializations` default, srgb 0.985 → 0.945 |

1024×1024, `idiom: vision`, scale `2x`. The three design groups map onto the three parallax layers
one-for-one.

**The ordering trap, which actool named exactly:** in a `.solidimagestack` the **first** entry in
`layers` is FRONT-most and the **last** is back-most — which must be a fully opaque bitmap. Listing
`[Back, Middle, Front]` fails with *"The last visionOS App Icon Layer with content, 'Front', must be
a fully opaque bitmap. The pixel at position (0, 0) has an alpha value of 0."* The correct order is
`[Front, Middle, Back]`.

### Verified

- `actool App/Assets.xcassets --platform xros --app-icon GlassPowerTools`: **zero errors**,
  `Assets.car` 4.4 MB, partial plist declaring `CFBundleIcons → CFBundlePrimaryIcon`.
- visionOS **device** Release build: `Assets.car` in the bundle, `CFBundlePrimaryIcon =
  GlassPowerTools`.
- iOS device build keeps its Icon Composer icon (`CFBundleIconName = GlassPowerTools`), and macOS
  keeps `GlassPowerTools.icns` + `CFBundleIconFile` — the stack does not disturb the square platforms.

**Limitation, same class as the one above: nobody has *seen* it render.** The bundle carries the
icon; whether the layer depth and the gradient read well against visionOS's own lighting needs the
device and a person.
