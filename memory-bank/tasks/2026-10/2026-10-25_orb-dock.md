# 2026-10-25 — Orbs gather in a dock on Vision Pro (D88)

## Objective and authorization
The owner, from two headset captures of four session orbs and the Connections orb, each a window of its own:
"an invisible 'canvas' where (when enabled) a user's windows (when the orb mode is clicked) would move automatically
into a 'dock' that itself can be moved around. I'd resize the connections orb to match, and include it too. We also
need to add Editor, Database, and Desktop to the orb so it's more of a machine nav than just tabs for a Terminal
window." Then: "We could create a liquid 'Water drop' effect when they go to the dock!" His choices are in D88.

## Platform
visionOS opens a new window above, below, leading or trailing another (`WindowPlacement.Position`, visionOS 2+, read
in Apple's documentation 2026-10-25) and moves none already open. So a window docks by closing into its orb, its
sessions kept, and comes back above the dock when its orb is pinched (`defaultWindowPlacement`, queued per request).

## Built
- **Setting:** Settings ▸ Appearance ▸ Orbs ▸ Shrink to Orb: Where the Window Is (default) / Into the Dock
  (`GlassOrbDock.settingKey`, this device's).
- **Dock:** `GlassOrbDockView` in its own `Window` ("Orbs", plain, content-sized, never restored), inside every
  capability's bootstrap as All Windows is, counted by window recovery. Connections orb first; one orb per docked
  terminal window; one per machine for docked databases, desktops and editors opened from the library. It closes
  itself when it holds nothing but Connections and Connections is open.
- **Docking:** `GlassSessionOrbModifier.shrink` with the setting on: the window gathers into a drop
  (`GlassOrbDropDeparture`), its orb lands in the dock (`GlassOrbDropArrival`: falls stretched, squashes, wobbles, a
  ripple), the window closes. `GlassOrbDockModel` keeps the ids and sizes; any way back (the orb, Active, All
  Windows, the library) takes the window out of the dock at its size (`windowAppeared`).
- **Sessions kept while docked:** terminal (nothing ended a workgroup with its window; its window counts as open for
  W15); database (`forgetWorkspace` instead of `releaseWorkspace`, which disconnected); desktop (the primary
  viewport stays attached, as `detach` of the last one closed the session); editor (`forget` keeps a docked clean
  workspace).
- **Connections:** idle with the setting on, the window closes into the dock (`holdsConnections`); the dock's
  Connections orb opens it above the dock.
- **The ring:** `GlassOrbServices` (all platforms, tested) decides which of the machine's services, each with its
  open session; `orbServiceDots` draws them, faint while not open, a pinch opening or bringing forward. The
  machine's Editor is its project opened last (`GlassSessionOrbServices.editor`). An editor opened from a terminal's
  folder button records the terminal window (`GlassOpenSession.openedFrom`, `GlassEditorRuntime.note`) and is on
  that terminal's ring, in place or in the dock; docked, it is on the terminal's orb while that is docked too, else
  on its machine's.

## Seventh round: windows come back as they were left
The owner, 2026-10-26, while testing 0.4.533: "let's have windows respawn in their last used state. In the dock vs.
open? Possible?" At launch only the terminal's windows come back (W15's list; databases, desktops and editors have
restoration off and never come back), and Connections (the system restores it). So:
- **Terminal windows:** the reopen record gains `asOrb` (in the dock or standing as its orb, and the size it grows back
  to), read from `GlassOrbDockModel` when the list is written (`TerminalWorkgroupsToReopen.orbsNow`). At launch a docked
  one is put in the dock, its window not opened, and the dock opened; a standing one opens as its orb
  (`opensAsOrb` → the window's `.task(id: dockID)` → `standAsOrb(growingBackTo:)`); the rest open as before.
- **Connections:** left in the dock (`holdsConnections`, now kept in the run's settings defaults under
  `com.glasspowertools.orbs.connectionsInDock`), the launch's window waits for the reopened terminals to connect or
  fail (`GlassOrbDockModel.lastRunCameBack`, set by the reopen; up to 40 s, SSH's 30 s timeout and a margin), then
  goes back into the dock — unless something is presented on it or it is in use (a password asked for, a host key,
  what failed: the reopen says these on the window that ran it, Connections at launch), or it was asked for. Found by
  the first relaunch test: the demo machine's missing password was an alert on Connections, and docking would have
  closed it. Quit as its orb, visionOS brings it back orb-sized: it becomes the orb
  again (until now it grew back to the library — W39's fix for a window drawn at the orb's size).
- `--demo-reopen open|dock|orb` (DEBUG, `--ui-testing` only, when the last run left nothing) stands for a last run with
  one terminal window on the first seeded machine; `UITests/GlassOrbRelaunchUITests.swift` quits and relaunches under
  one run (its store kept) three times per test.
- Backups of the changed files: `<work>/reopen-orbs/before/`.
- Two launch traps the relaunch tests found and fixed: Connections, asked to close two seconds into a launch as the
  dock was asked for, stayed open, dimmed — it now waits for the dock to be on screen (`intoDock` awaits
  `isShown`); and the demo's machine had no terminal settings behind its seeded service, so the seeding takes a
  service id (`alpha:ssh=<uuid>`, DEBUG) and `--demo-reopen` saves settings on it.
- Validation: `GlassOrbRelaunchUITests` (5) quit and relaunch under one run: a docked window back in the dock and a
  pinch brings it out, then back open; a standing orb back as its orb, then open; Connections back into the dock, then
  open; Connections staying open for a question; the dock resized tall standing in a column and opening at that size
  next launch. Unit: `TerminalWorkgroupReopenTests` (10, two new), each of four breaks of the record caught.

## Eighth round: the dock's shape and its own look
His asks (2026-10-26): "could we make it responsive? A user could then make it vertical with simply resizing it so
… Do we need a Dock Settings … Glass/transparency options for the dock? Vertical/horizontal?" Asked, he chose its
shape decides, and its own glass and Opacity starting with Appearance.
- The dock window is `.contentMinSize` (it was `.contentSize`, which bounced every resize back). Taller than wide,
  its orbs stand in a column (`VStackLayout`, every cell a ringed one's width so the orbs share one line and names
  open beside them); otherwise a row; past what fits, it scrolls. Carrying an orb works along either.
- Until resized it fits its orbs in a row (`GlassWindowSizer`, as before but asked for); a size it did not ask for is
  the person's, kept under `com.glasspowertools.orbs.dockSize` and opened at (`glassOrbDockOpensAtItsSize`).
  Settings ▸ Appearance ▸ Orbs ▸ Fit Dock to Its Orbs clears it.
- Its look: `GlassWindowOverrides` under `com.glasspowertools.orbs.dockLook`, painted as every window's
  (`GlassLayeredWindow` + `glassSpatialWindowGlass`), and set with the This Window rows (`GlassWindowLayerControls`,
  which gained a section title: "Dock").
- A layout loop found on the way: `.containerRelativeFrame` on the scroll view's content, its axis flipping with the
  shape, kept the main thread busy in a column (the runner: "process main thread busy"); plain fill frames replaced it.
- `--demo-dock-resize WxH` (DEBUG) stands for the person's resize; the runner cannot drag a window's corner.
